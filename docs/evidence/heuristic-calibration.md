# Heuristic prefilter calibration

Evidence behind `core/heuristics/`. Every number here was produced by
`node test/heuristics-calibration.bench.mjs`; rerun it to reproduce. Nothing in
this document is an inference from a datasheet — where a question could not be
answered by measurement, it says so and the corresponding threshold is not
shipped.

Environment for the run recorded below:

```
node v24.15.0 | sharp 0.34.5 | libvips 8.17.3 | win32 x64
11th Gen Intel(R) Core(TM) i7-1165G7 @ 2.80GHz
```

## What ships, and what does not

| Analysis | Ships | Can reject | Threshold |
| --- | --- | --- | --- |
| Blank / near-uniform frame | yes | yes | CIEDE2000 just-noticeable difference (1.0), from the formula's own scaling |
| Dominant palette | yes | no | none — descriptive |
| Brand-colour presence | yes | yes | derived per colour from the project's existing ±3-per-channel tolerance |
| Perceptual hash + Hamming distance | yes | only with a caller-supplied threshold | **none shipped** |
| Text likelihood from edge/stroke density | **no** | — | — |

## 1. Duplicate detection: distance shipped, threshold refused

Corpus: 24 procedurally generated "design assets" at 512px (flat background, two
to four solid shapes, one accent band), each put through 13 transforms. 312
same-image pairs and 276 different-image pairs.

```
SAME IMAGE (all transforms) n=  312  min=  0  p50=  0  p95= 10  p99= 16  max= 18  mean=1.51
DIFFERENT IMAGES            n=  276  min= 22  p50= 32  p95= 38  p99= 42  max= 42  mean=31.78
```

Per transform, worst case out of 24:

| Transform | p50 | max |
| --- | --- | --- |
| PNG recompress | 0 | 0 |
| JPEG q90 / q40 / q15 | 0 / 0 / 0 | 2 / 2 / 4 |
| Rescale 0.5x / 0.9x / 2x | 0 / 0 / 0 | 0 / 2 / 2 |
| Brighten +8% / darken −8% | 0 / 0 | 2 / 6 |
| Blur 1px | 0 | 2 |
| Crop 2% | 2 | 4 |
| Rotate 1° | 4 | 12 |
| Crop 10% | 10 | 18 |

On this corpus the classes separate: worst same-image distance 18, closest
different-image distance 22.

**So why is no threshold shipped?** Because that separation is not strong enough
to become project behaviour:

- The gap is four bits out of sixty-four, and it is a gap between two *extreme
  order statistics* estimated from 24 base images and 276 different-image pairs.
  The quantity that matters for a prefilter that discards work is the tail of the
  different-image distribution, and 276 samples say almost nothing about it.
- The corpus is synthetic. It is generated by the same code, from the same
  primitive shapes, with the same flat backgrounds. Real generated output —
  several attempts at one prompt, which is exactly the duplicate case Pixelproof
  cares about — will produce near-miss pairs that are *genuinely different
  images* while sharing composition, palette and layout. Those pairs are the ones
  that would land in the gap, and none of them exist here.
- pHash's own documentation states that a DCT hash is not semantically
  meaningful and that its published threshold came from its corpus. Substituting
  this corpus for that one and calling the result calibrated would repeat the
  same mistake with less data.

`findDuplicates` therefore requires an explicit `maxDistance` and throws without
one, and `runPrefilters` reports the measured distance and takes no decision when
no threshold is configured. For a maintainer who has to choose a starting point,
this run supports the *conservative* end: a threshold of 10 or below catches
every re-encode, rescale, brightness change and small crop measured here while
staying twice as far from the observed different-image minimum. It also rejects
nothing, so it fails safe — a missed duplicate costs one model call, and a false
duplicate silently discards a good artifact.

The one property worth knowing before storing hashes: a uniform frame has no AC
energy, so **every blank frame hashes to `0000000000000000` regardless of
colour**. Blank detection is a separate prefilter for this reason, and the
degenerate case is pinned explicitly in `phash.mjs` — without that guard a
constant image's hash is floating-point rounding noise.

Hashes are also tied to the resampler that produced them: `lanczos3` is pinned,
but a libvips upgrade may still shift bits, so a stored corpus should record the
decoder version.

## 2. CIEDE2000 tolerance: no single default is defensible

`mechanical.mjs` derives ±3 per channel from three measured generation runs. That
per-channel tolerance was swept across sRGB (5,832 colours on a 15-step lattice,
taking the maximum over the ±3 cube at each point):

```
min radius 0.3824 at rgb(0,0,255)
max radius 6.2226 at rgb(30,30,30)
mean radius 1.7315

rgb(255,255,255) -> 2.4186    rgb(128,128,128) -> 5.0861
rgb(200,200,200) -> 4.7166    rgb(25,25,20)    -> 7.0135
rgb(0,0,0)       -> 1.9404    rgb(255,0,0)     -> 0.7073
rgb(0,102,204)   -> 1.3441
```

A tolerance the project already considers acceptable spans **0.38 to 7.01** in
CIEDE2000 terms — an order of magnitude — because CIEDE2000's chroma and
lightness weightings are not uniform across the space. Any single flat ΔE00
number would be far too tight on dark near-neutrals or far too loose on saturated
colours.

`deltaERadiusForChannelTolerance` therefore derives the radius per colour from
the existing ±3, rather than introducing a second, invented tolerance.

The implementation itself is validated against the published supplementary
dataset (Sharma, Wu and Dalal 2005): all 34 reference pairs agree to four
decimals, in `test/heuristics-color.test.mjs`.

## 3. Text likelihood: measured, then refused

Sobel edge density over the 256px sample, on scenes drawn to look like text and
scenes drawn to look like anything else:

```
0.8889  not-text  hatch-texture
0.7865  not-text  foliage-noise
0.5497  not-text  brick-texture
0.5071  text      paragraph-of-text
0.2431  not-text  chart-gridlines
0.0374  text      heading-only
0.0000  not-text  photo-like-gradient
```

Text spans [0.0374, 0.5071], and `chart-gridlines` — a plain grid, no glyphs —
lands at 0.2431, squarely inside it. No threshold separates the two classes, and
the ordering is not even monotonic: a hatch pattern out-scores a paragraph of
body copy.

That is disqualifying, because of *how the check would be used*. "No text in the
image" is one of the most common spec assertions, so a text-likelihood signal
would immediately become load-bearing on exactly the assertion it cannot support,
and it would fail in the most expensive direction: an image with a heading and
otherwise flat artwork (density 0.037) is indistinguishable from an image with
nothing in it, so a "no text" assertion would be marked satisfied when text is
plainly present.

No text-likelihood analysis ships in `core/`. The Sobel implementation exists
only inside the benchmark harness, as the evidence for this refusal. Text
detection needs a real detector — the model judges already look at the image, and
that is where the question belongs.

## 4. Cost at the maximum supported size

The longest supported edge is 3840 (`docs/V2-BRIEF.md`). Median of five runs,
after a warm-up run:

| Size | All three prefilters | Blank only | Palette + brand | Duplicate | JS luma pass over the 32×32 sample |
| --- | --- | --- | --- | --- | --- |
| 3840×2160 (8.3 MP) | 639.1 ms | 222.6 ms | 186.7 ms | 189.5 ms | 0.0299 ms |
| 3840×3840 (14.7 MP) | 888.0 ms | 328.5 ms | 279.6 ms | 259.4 ms | 0.0227 ms |

The plan's expectation holds: cost is decode-bound, and the JavaScript is
negligible. A full luma pass plus DCT over the hash sample is ~0.02–0.03 ms,
around one ten-thousandth of the total, because every per-pixel loop runs on a
32×32, 64×64 or 256×256 sample rather than on 14.7 million pixels.

Running all three prefilters decodes three times, once per sample size, which is
why "all three" is roughly the sum of the individual figures rather than the cost
of the largest. That is a deliberate trade: deriving the 64px and 32px samples
from the 256px one in JavaScript would cut the cost to about a third, but the
perceptual hash would then no longer be a `lanczos3` resample of the original,
and every stored hash would be tied to this project's own reduction code instead
of a conventional one. Sub-second against a model call measured in seconds is not
worth that.

## Bearing on ADR 0013

ADR 0013 defers four things. Two of them now have evidence:

- *Colour science beyond sRGB/D65 CIEDE2000* — the contract is implemented and
  validated against the published dataset, and the tolerance question is answered
  by derivation from the project's own measured ±3 rather than by a new constant.
  Alpha compositing remains a parameter with a stated default (white), not a
  decision.
- *Text likelihood* — measured and refused, with the data above. This one is
  decidable now, in the negative.

Two remain genuinely open:

- *The duplicate corpus and threshold* — still requires real generated output,
  for the reasons in section 1. The distance ships; the threshold does not.
- *Sampling and ICC handling* — sampling is bounded and stated, but ICC-aware
  decoding is untouched: everything here assumes the raw buffer is sRGB, which is
  what `sharp` returns without an explicit colour-management step.
